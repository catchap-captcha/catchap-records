# 미디어 버킷 분리 — 캡차가 강의 영상에 닿지 못하게 (2026-08-12 저녁)

## 왜 하나

0807 에 캡차 전용 S3 계정을 만든 이유가 문서에 있습니다.

> *"catchap-backend 의 S3 키는 미디어 15.45GB 에도 닿는다. 캡차가 뚫리면 강의 영상까지
> 같이 넘어간다. 역할이 다르면 열쇠를 나눈다."*

★**그런데 그 격리는 작동한 적이 없습니다.** 전용 계정의 역할도 `Object Storage 매니저`
하나였고, 버킷이 그 역할 그룹을 **`스토리지 관리자`(버킷 전체 관리)** 로 매핑하고 있었습니다.

★**같은 버킷 안에서는 프리픽스로 못 나눕니다.** 그래서 버킷을 나눕니다.

---

## 1. 먼저 확인한 것 — 버킷 권한이 어디까지 되나

```
권한 탭 하위   역할 / 접근(Access-Control) / CORS
접근 탭        ★퍼블릭 차단 토글뿐 — 계정별·프리픽스별 설정 ★없음
역할 탭 「역할 추가」가 받는 것
               클라우드 계정 · 역할 그룹 · ★서비스 계정        ← 계정 단위로 줄 수 있다
역할 9종       스토리지 관리자 / 편집자 / ★객체 관리자 / 객체 생성자 / 객체 뷰어
               / 버킷 편집자 / 권한 정책 뷰어 / 권한 정책 작성자 / 뷰어
```

★**서비스 계정 단위로 줄 수 있다는 것이 열쇠였습니다.** 계정을 다시 만들지 않아도 됩니다
(서비스 계정 역할은 생성 후 변경 불가라, 재생성은 kms11 명단 이탈로 이어집니다).

---

## 2. 🚨새 버킷에도 같은 매핑이 ★자동으로 붙습니다

`catchap-media-prod-team1` 을 만들자마자 역할 그룹 6건이 그대로 붙어 있었습니다.

```
프로젝트 관리자 → 스토리지 관리자      프로젝트 멤버 → 스토리지 편집자
프로젝트 리더   → 스토리지 뷰어        ★Object Storage 매니저 → ★스토리지 관리자
Object Storage 뷰어 → 스토리지 뷰어    클라우드 계정(소유자) → 스토리지 버킷 소유자
```

★**즉 「버킷만 나누면 된다」는 생각은 틀렸습니다.** 매핑을 손대야 의미가 생깁니다.

## 3. ✅한 일 — 더하고 나서 뺐습니다

```
① 더함   서비스 계정 catchap-backend → ★스토리지 객체 관리자
         (스토리지 관리자보다 좁다 — 버킷 설정·권한은 못 만진다)
② 뺌     역할 그룹 4개
           Object Storage 매니저   ← ★캡차가 가진 역할
           Object Storage 뷰어     ← ★매니저가 뷰어를 포함하므로 이것도 빼야 읽지도 못한다
           프로젝트 멤버           ← catchap-ci · catchap-github-actions
           프로젝트 리더           ← catchap-monitor · catchap-ops
③ 남김   프로젝트 관리자(사람) · 버킷 소유자 · catchap-backend
```

★**순서가 중요합니다** — 먼저 더하고 나중에 뺐습니다. 반대로 했으면 중간에 접근이 끊깁니다.

## 4. ✅권한이 실제로 되는지 먼저 시험했습니다

옮기기 전에 **백엔드 파드 안에서** 미디어 키로 찔러 봤습니다.

```
MEDIA 관련 env   MEDIA_BUCKET · MEDIA_KEY_PREFIX · MEDIA_S3_ACCESS_KEY ·
                MEDIA_S3_ENDPOINT · MEDIA_S3_REGION · MEDIA_S3_SECRET_KEY
LIST  catchap-storage-prod-team1   ok
LIST  catchap-media-prod-team1     ok
PUT / GET / DEL  새 버킷           ok
★결과: 백엔드 미디어 키로 새 버킷 읽기·쓰기 가능
```

★**이 시험을 안 했으면 옮긴 뒤에 「권한이 없다」를 알게 됐을 것입니다.**

```

  → copy_object 로는 안 되므로 ★멀티파트 복사(512MB 조각)로 넘김
이미 있는 키는 건너뜀 → ★중단돼도 다시 돌리면 이어서 함
```

## 6. ✅설정 교체 (PR #51) 와 재기동

```
전  MEDIA_BUCKET: catchap-storage-prod-team1
후  MEDIA_BUCKET: catchap-media-prod-team1     ← ★바꾼 줄은 하나뿐
```

올리기 전에 **중복 키를 거부하는 검사기**로 확인했습니다(낮에 그 검사를 안 해서 배포를
통째로 죽인 적이 있습니다 — README 4-5절).

⚠️★**ConfigMap 이 바뀌어도 파드는 스스로 다시 뜨지 않습니다.** 배포본에 체크섬 주석이
없어 `kubectl rollout restart deploy/backend-api` 로 **수동 재기동**했습니다.

```
21:39:10  ArgoCD 동기화 — ConfigMap 반영
21:39:23  재기동 완료 · 새 파드 2개가 catchap-media-prod-team1 을 들고 있음
```

## 7. ✅격리가 됐는지 — ★세 방향으로 확인

### ① 백엔드는 새 버킷에서 실제로 읽는가

```
media/lectures 5개 · 첫 파일 앞 12바이트 = 00 00 00 20 66 74 79 70 69 73 6f 6d
                                            → ★ftypisom = 진짜 MP4
```

### ② 캡차는 새 버킷에 못 닿는가

```
미디어 버킷 LIST   막힘 (AccessDenied)
미디어 객체 GET    막힘 (AccessDenied)
미디어 버킷 PUT    막힘 (AccessDenied)
★대조군 — 캡차 자기 버킷 LIST: 정상
```

★**대조군이 핵심입니다.** 그게 없으면 「키가 죽어서 막힌 것」과 구분이 안 됩니다.

### ③ 옛 버킷의 사본도 지웠는가

★**여기가 진짜 마지막입니다.** 새 버킷을 막아도 **옛 버킷에 사본이 남아 있으면
캡차는 그걸 읽습니다.** 지우기 전에 실제로 읽히는 것을 확인했습니다.

```
지우기 전  캡차 → 옛 버킷 media/lectures  3개 · ftypisom ★읽힘
지우기 직전 재대조  옛 3,476개 ↔ 새 3,476개 · 빠진 것 0 · 크기 다른 것 0
삭제       3,476개 (21:43:28 → 21:43:52)
지운 뒤    옛 버킷 media/ ★0개 · 새 버킷 3,476개 15.68GB 그대로
           캡차 → 옛 버킷 media/lectures  ★0개
```
