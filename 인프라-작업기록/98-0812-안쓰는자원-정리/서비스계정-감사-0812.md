## 2. ⚠️★제가 틀렸던 것 — 「매니저가 과하다」는 오판이었습니다

처음 감사에서 *"앱은 읽기만 하니 `Secrets Manager 뷰어`로 낮추자"* 고 적었습니다. **틀렸습니다.**

### 공식 문서 원문

> **Secrets Manager 뷰어(Viewer)**: 시크릿의 목록, 상태, 버전 정보 등 리소스를 조회할 수
> 있는 권한을 가집니다. **단, 시크릿 값을 조회하거나** … **수행할 수 없습니다.**

> **Secrets Manager 매니저(Manager)**: … **시크릿 값 조회** 등 … **KMS 사용자(User) 역할
> 이상이 추가로 필요**합니다.

★**즉 「매니저 + KMS 사용자」가 앱이 비밀값을 읽을 수 있는 최소 조합입니다.** 중간 단계가 없습니다.

### 그대로 했으면 어떻게 됐나

```
① 서비스 계정 역할은 ★생성 후 변경 불가 → 낮추려면 계정을 ★지우고 다시 만들어야 한다
② 다시 만들면 계정 ID 가 바뀐다
③ 그러면 ★kms11 접근 명단에서 빠진다 → 복호화 자체가 안 된다
④ 필수 변수 관문 때문에 앱 4개가 ★기동 실패
= 보안을 높이려다 서비스를 통째로 내릴 뻔했습니다
```

★**남길 것** — 「최소권한」은 원칙이지만, **그 플랫폼에 더 낮은 단계가 실제로 있는지**를
먼저 확인해야 합니다. 이 판정은 0730 에 이미 문서로 확정해 둔 것이었는데
(`93-참고자료/04-권한시험기록.md`) **제가 그 기록을 안 찾아보고 원칙만으로 판단했습니다.**

## 3. 🚨★진짜 문제 — 캡차↔미디어 격리는 ★작동한 적이 없습니다

0807 에 `catchap-captcha-object-storage` 를 **따로 만든 이유**가 문서에 남아 있습니다.

> *"catchap-backend 의 S3 키는 미디어 15.45GB 에도 닿는다. 캡차가 뚫리면 강의 영상까지
> 같이 넘어간다. 역할이 다르면 열쇠를 나눈다."*

### 그런데 그 전용 계정의 역할도 `Object Storage 매니저` 하나였습니다

그리고 **버킷에 역할 그룹 매핑이 걸려 있습니다**(0730 실측).

```
버킷 catchap-storage-prod-team1 · 권한 탭 · 역할 그룹 6건 중
  프로젝트 관리자        → 스토리지 관리자
  프로젝트 멤버          → 스토리지 편집자
  프로젝트 리더          → 스토리지 뷰어
  ★Object Storage 매니저 → ★스토리지 관리자     ← 버킷 ★전체 관리
  Object Storage 뷰어    → 스토리지 뷰어
```

★★**즉 `Object Storage 매니저`를 가진 계정은 그 버킷 전체의 관리자입니다.**
전용 계정을 만들어도 **`media/lectures` 15.53GB 에 그대로 닿았습니다.**

```
설계 의도   캡차는 captcha-service/ 만 · 미디어는 못 본다
실제        ★역할이 같으므로 접근도 같다 — 나눈 효과 0
지금        전용 계정을 없애고 catchap-captcha 로 합쳤으니 ★상태는 그때와 동일
```

**나쁜 것은 「합쳤다」가 아니라 「나눴다고 문서에 적혀 있었다」는 것입니다.**
있다고 믿는 방어가 없는 것이, 없는 줄 아는 것보다 위험합니다.

### 고치려면

```
IAM 역할은 프로젝트 단위라 프리픽스로 못 좁힙니다. 실질적인 길은 둘뿐입니다.
  ① 버킷을 나눈다 — 미디어를 별도 버킷으로 옮기고 역할 그룹 매핑을 달리한다
  ② 버킷 「접근(Access-Control)」 탭에 계정별 항목을 두고 역할 그룹 매핑을 뺀다
     ⚠️매핑을 빼면 catchap-backend·catchap-ops 도 같이 막힙니다 — 순서를 짜야 합니다
```

⬜**반납 일정을 보면 지금 당장 고칠 일은 아닐 수 있습니다.** 다만 *"왜 나눴다고 적어 놓고
실제로는 안 나뉘었나"* 는 심사에서 나올 수 있어 **알고 답할 수 있어야 합니다.**

## 4. ⚠️`catchap-ci` 와 `catchap-github-actions` 의 분리는 이름뿐입니다

```
catchap-ci              프로젝트 멤버(Member)  1개
catchap-github-actions  프로젝트 멤버(Member)  1개   ← ★완전히 같음
```

나눈 이유는 *"GitHub Actions 는 이미지 push 전용"* 이었는데 **권한이 같습니다.**
오늘 확인한 대로 멤버 토큰이 주는 레지스트리 권한은 `pull,push` 입니다.

```
얻은 것    ★키를 따로 돌릴 수 있다 · 사고 시 한쪽만 끊을 수 있다 · 로그에서 구분된다
못 얻은 것  ★권한 격리
```

★**더 좁힐 방법이 현재 없습니다** — IAM 역할 25개에 **Container Registry 역할 자체가 없습니다**
(0812 확인). 「이미지 push 만」 같은 역할을 만들 수 없습니다.
→ **분리 자체는 그대로 두는 것이 맞습니다.** 얻는 것이 0은 아니기 때문입니다.

## 5. ⚠️`catchap-ops` 의 `Codeflow 매니저` — 안 쓰지만 ★빼지 않는 편이 낫습니다

Codeflow·Deployflow 는 **퍼블릭 클러스터 전용**이라 우리 구성에서는 못 씁니다.
원칙대로면 빼야 합니다. 그런데,

```
서비스 계정 역할은 ★변경 불가 → 빼려면 catchap-ops 를 ★다시 만들어야 한다
다시 만들면 ID 가 바뀌고 → ★kms11 접근 명단에서 빠진다
그러면 운영 계정으로 ★시크릿 값을 못 읽는다
```

★**득(안 쓰는 역할 1개 제거) 보다 실(운영 계정 복구 작업)이 큽니다.** 문서에 남기고 둡니다.
