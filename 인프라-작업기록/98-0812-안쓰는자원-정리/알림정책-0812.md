```

```

우리 VM 6대는 **모니터링 에이전트가 깔려 있지 않아 CPU 를 아예 보내지 않습니다.**

> **「3팀 GPU 가 바빠졌을 때 우리 팀 5명에게 메일이 가는 것」** 이었습니다.

### 그래서 어떻게 했나

- 필터를 우리 VM 6대로 걸어 **남의 서버로 우리가 깨는 일은 없게** 했습니다.
- 대신 **지금은 울리지 않는다**는 사실을 여기에 적어 둡니다. 지우지 않은 이유는

- ★VM CPU 감시는 **우리 모니터링 스택(VM2 의 Prometheus·Grafana)** 이 맡고 있습니다.
  Alert Center 는 **관리형 서비스(MySQL·Valkey·LB)** 쪽을 맡는 것으로 역할을 나눕니다.

⚠️**필터는 `instance_id` 밖에 없습니다**(`instance_name` 이 없음). 그래서 UUID 앞 8자리를
`|` 로 이어 적었습니다. **노드 풀을 새로 만들면 UUID 가 바뀌므로 이 필터는 낡습니다.**

```

                  ↑GPU노드  ↑GPU노드   ↑워커      ↑워커      ↑VM1      ↑VM2
```

⚠️값 칸에는 **길이 제한**이 있습니다. UUID 36자를 6개(221자) 넣으면 **아무 말 없이 안 들어갑니다**
— 「추가」 단추가 계속 회색입니다. 8자리로 줄여 65자로 맞췄습니다.

## 5. ★임계치를 정하기 전에 「지금 값」을 봤습니다

알림 정책 만들기 화면 오른쪽 **예상 알림 차트**는 실제 값을 그려 줍니다.
이걸 안 보고 숫자만 넣었으면 밤새 오탐이 왔을 자리가 두 군데 있었습니다.

### ① `memstore_connected_slaves` — 계열이 두 개다

```
계열 1  replication_role=replica  ★0.00   ← 복제본 자신은 슬레이브가 0개
계열 2  replication_role=primary   1.00
```

「1 미만이면 알림」을 **필터 없이** 걸었으면 **계열 1 때문에 항상 참**이 됩니다.
`replication_role = primary` 필터를 넣자 차트가 1.00 한 줄로 정리됐습니다.

### ② `lb_unhealthy_host_count` — 한쪽이 음수다

```
catchap-lb-2b (pool_7710b3c6…)   0.00
catchap-lb-2a (pool_de74b641…)  ★-1.00   ← 「모름」을 -1 로 보내는 것으로 보임
```

`1 이상`이라 -1 은 걸리지 않아 오탐은 없습니다. 다만 ★**lb-2a 는 이 조건으로는
영원히 울리지 않습니다.** 그래서 `lb_healthy_host_count < 1`(긴급) 조건을 같이 넣었습니다
— 이쪽은 두 대 모두 1.00 을 정상적으로 보고합니다.

캡처 `55-MemStore-복제개수-실측` · `56-MemStore-primary필터-적용` ·
`60-LB-조건1-예상차트` · `61-LB-조건2-정상대상0-차트`
